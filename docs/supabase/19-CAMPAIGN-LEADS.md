# CAMPAIGN_LEADS

## 1. What is this table?

`campaign_leads` is the junction between campaigns and contacts — it tracks which contacts have been enrolled in which campaign, their current status in the send lifecycle, and the outcome of outreach (replies, bounces, unsubscribes).

**Schema confirmed:** All columns, constraints, and status values below are verified from the live database and TypeScript source (`src/db/campaign-leads.ts`), confirmed through Stage 19B (enrollment) and Stage 20 (provider upload) end-to-end testing.

## 2. Why does this table exist?

A campaign can have hundreds of leads; a contact might be in multiple campaigns over time. This table is the roster of who's in each campaign, what stage of the send lifecycle they're at, and what happened to each of them.

## 3. What data does it store?

| Column | Type | Default | What it means |
|--------|------|---------|---------------|
| `id` | uuid | gen_random_uuid() | Unique identifier |
| `campaign_id` | uuid NOT NULL | — | Which campaign → `campaigns(id)` |
| `contact_id` | uuid NOT NULL | — | Which contact → `contacts(id)` |
| `client_id` | uuid NOT NULL | — | Which client → `clients(id)` (added Stage 15) |
| `status` | text NOT NULL | `'ready'` | Current lifecycle status (see status values below) |
| `platform_lead_id` | text | NULL | Provider-assigned lead ID. **Currently always NULL** — Smartlead's upload API returns aggregate counts only, not per-lead IDs. Backfilled by GET /campaigns/{id}/leads in Stage 21+. |
| `sent_at` | timestamptz | NULL | When the first email in the sequence was sent to this contact |
| `replied_at` | timestamptz | NULL | When a reply was received (null if no reply) |
| `reply_type` | text | NULL | Classification of the reply: `positive` \| `negative` \| `auto_reply` \| `out_of_office` |
| `created_at` | timestamptz NOT NULL | — | When this contact was enrolled (set explicitly — no trigger) |
| `updated_at` | timestamptz NOT NULL | — | Last state change (set explicitly — no trigger; `markLeadsUploaded` advances this) |

### Status values (confirmed live CHECK constraint)

```
ready          ← initial state on enrollment; eligible for upload
uploaded       ← successfully submitted to outreach provider (Stage 20)
queued         ← provider has scheduled the first email
sending        ← provider is actively working through the sequence
sent           ← at least one email has been delivered
replied        ← a reply was received (unclassified)
positive_reply ← reply classified as interested / wanting to meet
negative_reply ← reply classified as not interested
bounced        ← email hard-bounced
unsubscribed   ← contact unsubscribed
stopped        ← manually stopped (e.g. do-not-contact flag)
```

**State machine:** `ready → uploaded → queued → sending → sent → (replied | bounced | unsubscribed | stopped)`

`ready` and `uploaded` are managed by the application layer (Stage 19B + 20). All subsequent transitions come from Smartlead webhooks or the outcome-sync polling task (Stage 21+).

## 8. Security

**RLS enabled, zero policies defined (FINDING 6).**

`service_role` (used throughout) bypasses RLS — no application-layer impact today. The `anon` key cannot access this table. Before exposing campaign_leads to any user-facing query, tenant-isolation policies (`USING (client_id = ...)`) must be added. See `25-SUPABASE-SECURITY.md`.

## 9. No DB triggers

There are no triggers on `campaign_leads` (confirmed live). `updated_at` must be set explicitly on every INSERT and UPDATE. Application code is responsible.

## 10. What comes before it?

1. `campaigns` must exist and be in `draft` status with a `platform_campaign_id` set
2. `contacts` must exist with a verified email (`email_status = 'VERIFIED'`)
3. `account_intelligence` must exist for the contact's company with `opportunity_score > 0`
4. `contact_suppression` must have no active record for this contact under this client
5. Contact must not already be enrolled in this campaign (unique constraint)

All five gates are evaluated by `enrollContacts()` (`src/lib/lead-enrollment.ts`) before any row is written.

## 11. What comes after it?

- **Stage 20 — `uploadCampaignLeads()`**: reads `status='ready'` rows, submits to outreach provider, transitions to `status='uploaded'`
- **Stage 21+ — outcome sync**: reads `status='uploaded'` rows, polls Smartlead for status progression, transitions through `sent → replied → positive_reply / negative_reply / bounced`
- **`/positive-reply-scoring`** — reads `reply_type` and `replied_at` to score campaign performance

## 12. Simple mental model

`campaign_leads = the send roster for each campaign — who's in, what happened to them, and where in the sequence they are.`

Each row is one (campaign, contact) pairing. The row is created at enrollment (`ready`), updated at upload (`uploaded`), and then updated again as Smartlead processes the sequence.

## 13. SQL to inspect it

```sql
-- All leads for a campaign, with status breakdown
SELECT status, COUNT(*) as count
FROM campaign_leads
WHERE campaign_id = '<campaign-uuid>'
GROUP BY status
ORDER BY count DESC;

-- Specific lead — full row
SELECT id, campaign_id, contact_id, client_id, status,
       platform_lead_id, sent_at, replied_at, reply_type,
       created_at, updated_at
FROM campaign_leads
WHERE id = '<lead-uuid>';

-- Ready leads for a campaign (eligible for upload)
SELECT cl.id, c.email, c.first_name, c.last_name, cl.created_at
FROM campaign_leads cl
JOIN contacts c ON c.id = cl.contact_id
WHERE cl.campaign_id = '<campaign-uuid>'
  AND cl.client_id   = '<client-uuid>'
  AND cl.status      = 'ready'
ORDER BY cl.created_at ASC;

-- Uploaded leads (in Smartlead, platform_lead_id still null until Stage 21+)
SELECT cl.id, c.email, cl.status, cl.platform_lead_id, cl.updated_at
FROM campaign_leads cl
JOIN contacts c ON c.id = cl.contact_id
WHERE cl.campaign_id = '<campaign-uuid>'
  AND cl.status      = 'uploaded';

-- Check for a specific contact's enrollment status
SELECT cl.status, cl.platform_lead_id, cl.created_at, cl.updated_at
FROM campaign_leads cl
WHERE cl.campaign_id = '<campaign-uuid>'
  AND cl.contact_id  = '<contact-uuid>';

-- Positive replies for a campaign
SELECT c.email, cl.replied_at, cl.reply_type
FROM campaign_leads cl
JOIN contacts c ON c.id = cl.contact_id
WHERE cl.campaign_id = '<campaign-uuid>'
  AND cl.reply_type  = 'positive'
ORDER BY cl.replied_at DESC;
```

## 14. Stage 20 — Confirmed Smartlead upload behaviour

The following was confirmed through end-to-end live testing on 2026-09-05:

### What the upload API returns

```json
{
  "ok": true,
  "upload_count": 1,
  "already_added_to_campaign": 1,
  "duplicate_count": 0,
  "total_leads": 0,
  "skipped_in_other_campaign_count": 0,
  "block_count": 0,
  "invalid_email_count": 0,
  "invalid_emails": [],
  "unsubscribed_leads": [],
  "is_lead_limit_exhausted": false,
  "lead_import_stopped_count": 0,
  "bounce_count": 0
}
```

### Field semantics

| Field | Meaning |
|-------|---------|
| `upload_count` | Leads accepted (may still be 1 for idempotent re-uploads) |
| `already_added_to_campaign` | **Per-campaign dedup counter** — non-zero on idempotent re-upload of an existing lead. This is the authoritative dedup signal. Mapped to `duplicateCount` internally. |
| `duplicate_count` | **Global suppression/unsubscribe counter** — leads blocked by global lists, not by campaign membership. Different meaning from `already_added_to_campaign`. |

### `ignore_duplicate` is NOT a valid parameter

`?ignore_duplicate=true` was removed from the Smartlead upload URL during Stage 20 testing. Including it causes HTTP 400: `"ignore_duplicate" is not allowed`. Smartlead handles dedup natively; no extra parameter is needed. See adapter JSDoc in `src/providers/outreach/smartlead.ts`.

### `platform_lead_id` always NULL after upload

Smartlead's `POST /campaigns/{id}/leads` returns aggregate counts only — no per-lead IDs. `campaign_leads.platform_lead_id` remains `NULL` after `uploadCampaignLeads()` completes. Stage 21+ will use `GET /campaigns/{id}/leads` to backfill these IDs by matching on email address.

### Idempotency

Calling `uploadCampaignLeads()` a second time on the same campaign is a confirmed no-op:
- `getReadyLeadsForUpload` returns 0 rows (all already `uploaded`)
- The orchestrator returns early before any provider call
- 0 Smartlead POSTs, 0 DB writes, `readyCount=0`

If the process crashes between a successful provider call and the DB `markLeadsUploaded` update, the row remains `ready`. On retry, Smartlead returns `already_added_to_campaign=1` (not an error). The DB is then updated correctly. No data loss.

### Test evidence (2026-09-05)

| Phase | Result |
|-------|--------|
| Dry run (dryRun=true, limit=1) | 1 ready lead found, 0 provider calls, 0 DB writes |
| Live upload — first attempt | HTTP 400 from `?ignore_duplicate=true` (invalid param); row stayed `ready` |
| Adapter fix applied | Removed `ignore_duplicate`; added `already_added_to_campaign` to response interface; 14 new unit tests; 968/968 regression pass |
| Reconciliation (dryRun=false, limit=1) | Smartlead: `upload_count=1, already_added_to_campaign=1`; DB: `ready → uploaded`; `updated_at` advanced |
| Idempotency rerun | 0 provider POSTs, `readyCount=0`, DB unchanged, campaign remained DRAFTED |
| Smartlead campaign status throughout | `DRAFTED` — no activation, no email sent |

### Critical findings

#### Finding 1: `roster.sent_at` is UNRELIABLE — do not use for send detection

**`GET /campaigns/{id}/leads → sent_at` stayed `null` after a confirmed send.**

This field is NOT populated by Smartlead after a send completes. Any sync logic that polls `roster.sent_at` to detect sends will silently miss every send event.

**Do not use `roster.sent_at` as a send signal.**

#### Finding 2: `global_lead.last_sent_at` is the authoritative send timestamp

`GET /leads/?email=... → lead_campaign_data[].last_sent_at` transitioned from `null` to a real timestamp (`2026-09-07T08:01:57.411+00:00`). This is the **only per-lead send timestamp that Smartlead populates**.

`last_activity_at` equals `last_sent_at` when send is the most recent activity.

#### Finding 3: Status string `COMPLETED` confirmed for fully-sequenced leads

A lead whose entire sequence has been processed goes `STARTED → COMPLETED`. For a 1-step sequence, this happens after the single email is sent. For multi-step sequences, `INPROGRESS` is the intermediate state (not yet observed — requires a multi-step campaign).

**Status mapping (empirically confirmed):**

| Smartlead `status` | Meaning | Our DB `status` |
|--------------------|---------|-----------------|
| `STARTED` | Enrolled, sequence not yet begun | `uploaded` |
| `COMPLETED` | All sequence steps processed | `sent` (transition needed) |
| `INPROGRESS` | Mid-sequence | `sent` (unconfirmed — needs multi-step) |
| `BOUNCE` | Hard bounce | `bounced` (unconfirmed — not observed) |
| `UNSUBSCRIBED` | Unsubscribed | `opted_out` (unconfirmed — not observed) |

#### Finding 4: `lead_category_id` is null throughout

Not populated by a send event. Semantics unknown. Do not use until observed non-null.

#### Finding 5: `contacts.updated_at` EXISTS in live schema

Migration 0018 header documented this as a "confirmed" finding from pre-migration check (2026-09-07). The schema probe confirms `contacts.updated_at` is a `timestamp with time zone` column. The TypeScript `ContactRow` type does not yet include it. This enables richer staleness detection when the type is updated.

### Sync logic design (confirmed by evidence)

**To detect "was this lead sent?" per-lead:**
1. Call `GET /leads/?email=...` → check `lead_campaign_data[].last_sent_at` is non-null (authoritative)
2. Cross-check: `GET /campaigns/{id}/leads` → roster `status = COMPLETED or INPROGRESS` (secondary confirmation)
3. Roster `sent_at`: **ignore** — it is null even after a confirmed send

**To write to `campaign_leads`:**
- When global lead `last_sent_at` is non-null AND roster `status != STARTED`:
  - Set `status = 'sent'`, `sent_at = last_sent_at`, `updated_at = now()`
- When `last_reply_at` is non-null: set `status = 'replied'`, `replied_at = last_reply_at`
- When roster `status = BOUNCE`: set `status = 'bounced'`
- When `is_unsubscribed = true`: set `status = 'unsubscribed'`
